| GOV-01 | Everyone reads `PROGRESS.md` before writing code and before committing. Enforced by hooks and CI. | 2026-11-11 |
| ENG-01 | The ORM is Drizzle (already installed in `apps/api`). This replaces Kysely, which the engineering plan proposed. | 2026-11-11 |
| ENG-02 | Background jobs use pg-boss, so no Redis is needed. | 2026-11-11 |
| ENG-03 | Gherkin features live in `apps/*/features` and carry `@wip` until their story is built. CI runs every feature without `@wip` and fails on undefined or pending steps. Removing `@wip` is part of a story's Definition of Done. | 2026-11-11 |
| ENG-04 | Local dev and CI use one database image, built in `infra/postgres`: `pgvector/pgvector:0.8.0-pg16` plus the `postgresql-16-postgis-3` package. This answers E-05 for local dev and Testcontainers; the hosting side moved into E-03. `postgis/postgis:16-3.4` was dropped: it has no arm64 build and its apt repository is gone. | 2026-11-11 |
| ENG-05 | Tenant isolation in Postgres uses two database roles. `kiezruf_staff` reads reports where `tenant_path` is inside `app.scope_paths` and may change only `status` of reports whose tenant is in `app.write_paths`. `kiezruf_citizen` reads only the `public_report` view. Reading inherits down the tree. Changing a report needs a non-viewer role at the tenant that owns it, following the product plan ("Only the owner edits. Higher levels read and roll up."). So a tenant admin at Berlin level cannot change a Neukölln report. | 2026-11-11 |
| ENG-06 | Routing picks the deepest tenant whose boundary covers the point, and that tenant must be pilot or live; otherwise the answer is "not live here yet". The engineering plan's SQL filters by status first, which would send a report from a not-live Bezirk to the live city above it and contradict US-44 and `routing.feature`. | 2026-11-11 |
| ENG-07 | `report.location` is the public map position. `capture_location`, `capture_accuracy_m` and `capture_at` are private and are not in `public_report`. The engineering plan lists one location column. | 2026-11-11 |
| ENG-08 | Every API query runs under one of three database roles: `kiezruf_auth` (sign-in bookkeeping before the caller is known), `kiezruf_citizen` (public views; with `app.account_id` set, the citizen's own account, reports and votes, and posting as `processing` only) and `kiezruf_staff` (ENG-05). Report numbers come from a `SECURITY DEFINER` function, so citizens never touch `report_sequence`. In staging and production the API's login role gets the three roles `WITH INHERIT FALSE`. | 2026-11-11 |
| ENG-09 | Sessions are opaque random tokens, stored as SHA-256 hashes, sent as `Authorization: Bearer`. Citizens get 30 days. Sign-in codes are stored as HMACs keyed with `AUTH_SECRET`. No staff sessions are issued yet: staff need a second factor (passkey or TOTP) first. `@fastify/jwt` is installed but unused. | 2026-11-11 |
| ENG-10 | Parameters the product plan leaves open, to be confirmed: Me too counts as on-site within 150 m of the report (the duplicate-check radius); a report needs at least 1 photo; descriptions up to 1000 characters; 5 sign-in codes per address per hour; capture times up to 5 minutes in the future are accepted (clock skew). | 2026-11-11 |
| ENG-11 | `packages/shared` is one ES module (`"type": "module"`, a single `index.ts`). Node needs ESM to see its named exports, and relative imports inside the package would need file extensions that tsc NodeNext, Next and Metro do not agree on. | 2026-11-11 |
| ENG-12 | API coverage is measured on the integration tests (`pnpm --filter api test:int:coverage`, the CI integration job), because most API code needs a database. The unit-test figure for `apps/api` is no longer the one to watch. | 2026-11-11 |
| ENG-13 | Maps use MapLibre on web and mobile (answers E-04, product owner, 2026-11-11). No Google services. The style URL is configuration. The mobile app therefore needs an Expo dev build. | 2026-11-11 |
| ENG-14 | Notifications use an outbox: database triggers write a `notification` row in the same transaction as a report's status change (except the system publishing it) or a tenant going live; the worker delivers every minute. Push when it is on and the account has a device token, else email. Push payloads are generic text plus the report ID. Comments that trip the language filter are stored as `held`; the term list in `src/moderation/language.ts` is a seed for the moderation team. Account deletion is immediate (`delete_my_account()`), not within 30 days. Further parameters: a gallery photo without GPS accuracy counts as on-site only if the device is now within 100 m of it; extra photos in one report must be within 150 m of the first. | 2026-11-11 |
| ENG-15 | The app re-encodes photos to JPEG (long edge 2048 px) before upload, which also strips their EXIF, location included. The server therefore cannot check a photo's own metadata; the on-site evidence is the capture the client declares. The citizen web uploads originals. | 2026-11-11 |
| ENG-16 | The report flows call `POST /public/report-attempts` for their location check, so an attempt in a not-live area counts as demand (US-44); the map's tenant chip uses the read-only `GET /public/route`. The API trusts `X-Forwarded-For` only from the proxies in `TRUST_PROXY` (empty by default), so per-IP limits work behind the web server and cannot be dodged with a forged header. | 2026-11-11 |
| ENG-17 | Staff sign in with the email code plus TOTP (RFC 6238, any authenticator app), enrolled on first sign-in; staff sessions last 12 hours. TOTP secrets are encrypted at rest (AES-256-GCM, key derived from `AUTH_SECRET`); a code is never accepted twice; a challenge allows 5 tries. Passkeys may follow. Answers the open part of ENG-09. | 2026-11-11 |
| ENG-18 | Staff permissions: viewers read; case workers and tenant admins change the reports of the tenant that owns them; tenant admins also manage staff, thresholds, office name and contacts in their subtree and ban citizen accounts; platform admins configure (activate tenants, grant any role) but do not triage, following the product plan's ROLES (platform admin "edit: false"). Contacts saved at a higher node are usable below it. Every staff change writes `audit_event`. | 2026-11-11 |
| ENG-19 | Forwarding to the parent or a sibling tenant moves the report to that tenant (it keeps its ID); the original tenant reads it, read-only. Forwarding by email keeps the report with its tenant and editable. Bans are platform-wide and apply to citizen accounts only. Scores are stored in `report_score` and recomputed by the worker; a vote spike is flagged automatically and its new-account votes count half until a moderator clears it. | 2026-11-11 |
| ENG-20 | The AI provider is called through an OpenAI-compatible API (product owner, 2026-11-12): chat completions with a JSON schema for the briefing and for photos (category, confidence, a caption), and embeddings of that caption for photo similarity. The caption is never stored. Prompts are pinned in `src/ai/prompts.ts` with a version stored on each briefing; every call logs kind, model, input hash and latency, not the input. Without a configured provider the system runs without AI. Blur sits behind its own `BlurDetector` until E-10 is answered. | 2026-11-12 |
| ENG-21 | Phase 3 parameters, to be confirmed: category suggestions and duplicate checks are for signed-in citizens only, because uploads need a session (the prototype shows the suggestion before sign-in); the suggestion waits at most 3 s; originals over 15 MB are not processed; hotspots use DBSCAN with 150 m and 2 reports over the last 90 days in the same category group, computed on request rather than nightly; a place is recurring with 3 reports in 30 days and has a weekday pattern when more than half fall on one day; "acknowledged" in trends is the first status change of any kind; briefings go to every tenant taking reports and every node with staff above one; model output is pseudonymised again before it is stored. | 2026-11-12 |
| ENG-22 | Hosting and sign-in (product owner, 2026-11-12): the web app and console deploy to Vercel (`fra1`); Supabase (EU, Frankfurt) provides Auth and the Postgres database; the API and worker run on vlincta.com. Supabase Auth replaces the API's own email codes, sessions and staff TOTP (ENG-09 and ENG-17 are superseded): citizens sign in with a Supabase email code; staff also need Supabase MFA, and staff routes accept only `aal2` tokens whose TOTP check is at most 12 hours old. The API verifies Supabase access tokens itself (JWKS, or HS256 with `SUPABASE_JWT_SECRET`), links each Supabase user to an `account` row on first use (invited staff by their verified email), and deletes or bans Supabase users with the service-role key. A deleted account keeps its Supabase user id, so an unexpired token cannot recreate it. Migration 0012 removes every grant of Supabase's `anon` and `authenticated` roles, so its Data API reaches none of our tables. | 2026-11-12 |
